# LinLog 智能日志诊断与根因分析 Skill (AI-Native 规范)

## 1. 触发时机 (Trigger Scenarios)
当用户（包括测试人员、运营同学或研发工程师）在对话中满足以下任一条件时，Agent 应自主激活此 Skill（**无需用户要求输入命令**）：
- 用户提供了一个 `.zip` 文件路径或解压目录，并提出排查需求；
- 用户以非技术自然语言反馈：“帮我看看这个日志怎么回事”、“为什么用户说掉线了”、“为什么一直转圈卡顿”、“排查这个闪退/崩溃”、“查一下用户在这个时间段做了什么”；
- 用户要求还原特定用户在特定时间段内的行为流水与多领域时序因果。

## 2. 自动化分析工作流 (Workflow)

### 步骤一：自主执行日志特征抽取 (Zero-User-Friction)
Agent 应通过后台命令调用工程内置的诊断引擎，**自动利用持久化缓存，无需重复解压**：

1. **若用户有具体的问题或排查方向**（如排查重连、崩溃、卡顿、接口异常）：
   ```bash
   python3 tools/analyzer/analyze_log.py <path_to_zip> -q "<用户提问的关键词>"
   ```
2. **若用户需要全盘体检概览**：
   ```bash
   python3 tools/analyzer/analyze_log.py <path_to_zip>
   ```

### 步骤二：虚拟领域自适应与跨域因果推导 (Virtual Domain & Root Cause Analysis)
LinLog 遵循业务 0 侵入原则，接入方可在单文件、按文件名或分目录下记录日志。分析引擎已自动按 **【物理目录 $\to$ 文件名模式 $\to$ Tag/内容特征】** 弹性识别虚拟领域：
- **`network` 维度**：检查网络状态切换（Wifi/Cellular/NoNet）、API 慢请求（>800ms）及 4xx/5xx 错误；
- **`socket` 维度**：检查 WebSocket/TCP 连接状态切换（Connecting -> Connected -> Closed）及重连原因；
- **`apm` 维度**：检查 JVM 内存突增、系统可用内存告急、UI 卡顿与严重丢帧点（FPS < 30）；
- **`main` / `track` 维度**：检查用户行为轨迹（点击、进入页面）、主业务逻辑流转与异常堆栈。

### 步骤三：代码库联动与源码跳转 (Codebase Cross-Reference)
根据日志中提取到的核心 `Tag` 和异常堆栈，在当前工程中找到对应的 Kotlin 源码文件，建立因果证据链。

### 步骤四：输出《LinLog 架构级诊断报告》（双重视角结构）
必须同时兼顾**非技术人员（测试/运营）**的高效阅读诉求与**研发**的修复诉求：

```markdown
# 🩺 LinLog 智能日志体检与诊断报告

## 🟢 【测试 / 运营速读卡片】
1. **📢 事故大白话定性**：用通俗的语言说明发生了什么故障（例：“用户在 15:32 登录时因网络波动超时，导致未能进入主页”）；
2. **🎯 责任归属判定**：明确责任归属【前端 App 缺陷】/【后端接口超时/报错】/【用户弱网环境】/【第三方平台故障】；
3. **🚶 用户操作全链路还原**：按时间先后罗列用户操作（如：进入首页 $\to$ 点击登录 $\to$ 弹出加载中 $\to$ 提示连接失败）；
4. **💡 运营 / 测试处置建议**：
   - **给运营**：需要做什么补偿或用户沟通（如“无需退款，告知用户检查 Wi-Fi 后重试即可”）；
   - **给测试**：复现该 Bug 的关键步骤与边界条件（如“在弱网或网络断开瞬间发起请求”）。

---

## 🔍 【研发级技术深潜与证据链】
1. **⏱️ 跨域时序因果证据链**：按时间戳罗列【现场前操作 $\to$ 触发点 $\to$ 连锁副反应】的核心日志证据；
2. **💻 源码缺陷分析**：定位代码库中具体类、方法的漏洞、竞态或异常堆栈；
3. **🛠️ 修复建议与代码 Diff**：提供可落地的防重/异常防御 Kotlin 修复代码。
```
